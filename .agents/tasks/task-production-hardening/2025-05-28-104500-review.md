# Production hardening: Docker, Celery, observability, and Nginx TLS

A containerized production stack wrapping the existing EDMS FastAPI application. The change adds a multi-stage Dockerfile, an 8-service docker-compose topology (app, postgres, chromadb, minio, redis, celery-worker, celery-beat, nginx), Alembic migration infrastructure, a Celery task queue with Redis broker and graceful fallback, Prometheus metrics middleware, structlog-based structured logging, health/readiness probes, CI/CD workflows, and an Nginx reverse proxy with TLS termination and rate limiting.

**Watch for:** Redis ping on every dispatched task creates a per-request TCP roundtrip that can become a latency tax and a thundering-herd failure vector when Redis goes down (confirmed). The `/metrics` endpoint is unauthenticated and exposed through Nginx without IP restriction, leaking operational data to any caller (confirmed). Celery tasks use `asyncio.run()` which creates a fresh event loop per invocation — fine for worker processes but incompatible with contexts where a loop is already running (likely). The entrypoint script has no retry cap when waiting for PostgreSQL, so a misconfigured `DATABASE_URL` causes an infinite hang (confirmed).

## High-level view

The Docker build uses a two-stage pattern: a builder installs dependencies via `uv sync --frozen --no-dev`, and the final image copies only the virtualenv plus application code. The entrypoint waits for Postgres, runs Alembic migrations, then execs gunicorn with uvicorn workers. This is sound for a single-replica deployment but has no migration locking, so multiple replicas racing to start will all attempt `alembic upgrade head` concurrently.

Celery is introduced as an optional async processing layer. A `dispatch_task` utility checks Redis reachability and either routes to Celery or falls back to FastAPI's `BackgroundTasks`. The check is a synchronous `redis.ping()` on every call, which means the fallback decision is coupled to per-request network health rather than a cached/circuit-broken state.

Observability comes in three layers: Prometheus counters/histograms tracked via Starlette middleware, a `/metrics` scrape endpoint, and structlog with request-ID correlation and sensitive-key filtering. The metrics middleware normalizes path parameters to keep label cardinality bounded. Health probes are split into liveness (always OK) and readiness (database mandatory, Redis optional).

Nginx terminates TLS with self-signed certs (generated via a helper script), applies HSTS and security headers, rate-limits auth and API paths separately, and proxies WebSocket connections. The compose topology puts all backend services on an `internal` network and only exposes ports 80/443 through Nginx on an `external` bridge.

<summary>Issues (7)</summary>

1. **Redis ping per dispatch** — `is_celery_available()` opens a new Redis connection and pings on every task dispatch. Cache the result with a short TTL or use a circuit breaker to avoid per-request overhead and connection storms during Redis outages.
2. **Metrics endpoint exposed without auth** — `/metrics` is publicly accessible through Nginx. Add `allow`/`deny` directives or move it to a separate internal listener to prevent leaking operational data.
3. **Entrypoint infinite wait** — The `until python ...` loop has no retry counter or timeout. Add a max-attempts guard so a broken DATABASE_URL fails fast instead of hanging the container indefinitely.
4. **Migration race on multi-replica deploy** — Multiple containers starting simultaneously will all run `alembic upgrade head`. Use an advisory lock or a dedicated migration init-container to serialize.
5. **asyncio.run() in Celery tasks** — Each task creates a new event loop. Safe in dedicated worker processes today, but will break if tasks are ever invoked from within an existing async context (e.g., tests or future architectures).
6. **Readiness probe creates sync Redis connection** — The `/health/ready` endpoint instantiates a synchronous `redis.Redis` inside an async handler, blocking the event loop for up to 1 second on timeout.
7. **CI security job is best-effort** — `pip-audit` runs with `continue-on-error: true`, so vulnerable dependencies won't block the pipeline.

## Celery dispatch and the Redis-ping-per-call pattern

Every call to `dispatch_task` (used in document upload, backup trigger, and bulk processing) invokes `is_celery_available()`, which instantiates a fresh `redis.Redis` and calls `ping()` with a 1-second socket timeout. Under normal operation this adds ~1ms per request, but when Redis is unreachable the full second timeout fires on every request before falling back to `BackgroundTasks`. If many requests arrive simultaneously during a Redis blip, they all block their asyncio worker thread waiting on the synchronous Redis call, potentially exhausting the uvicorn worker pool.

```python
# app/tasks/utils.py
def is_celery_available() -> bool:
    try:
        r = redis.Redis.from_url(settings.REDIS_URL, socket_connect_timeout=1)
        r.ping()
        return True
    except Exception:
        return False
```

A cached flag with a 5-10 second TTL (or a simple circuit breaker that flips after N failures) would eliminate the per-request cost and degrade gracefully.

The same synchronous Redis pattern appears in the readiness probe (`/health/ready`), where a sync `redis.Redis.from_url` runs inside an `async def` endpoint. This blocks the event loop thread for up to 1 second. Using `redis.asyncio.Redis` would be consistent with the async handler context.

## Entrypoint wait-for-postgres loop

```bash
until python -c "..." 2>/dev/null; do
    sleep 2
done
```

This loop runs forever if the DATABASE_URL is wrong (e.g., typo in hostname). Containers in this state won't crash — they'll sit consuming resources without surfacing the real error. A `MAX_RETRIES=30` counter with an exit-1 on exhaustion would make misconfigurations fail visibly.

## Migration concurrency in multi-replica deployments

The entrypoint unconditionally runs `alembic upgrade head` before starting the app. In the current docker-compose topology only the `app` service hits this path (celery-worker and celery-beat override the command), so today's deployment is safe. The concern surfaces if this is deployed to Kubernetes with multiple app replicas: concurrent Alembic runs can produce duplicate migration attempts or deadlocks on the `alembic_version` table. The standard mitigation is a Postgres advisory lock inside `env.py` or a separate one-shot migration job.

## Prometheus metrics exposure

```nginx
location /metrics {
    proxy_pass http://app;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    # Optionally restrict to internal IPs:
    # allow 10.0.0.0/8;
    # deny all;
}
```

The commented-out restriction means metrics are publicly readable by default. Application metrics (request rates, error rates, active connections, storage usage) are useful for reconnaissance. Uncommenting the allow/deny block or binding metrics to a separate port that Nginx doesn't expose externally would close this.

## Sensitive-data filtering depth

The structlog sensitive-key filter matches top-level `event_dict` keys against a regex (password, token, secret, key, authorization, cookie). It won't catch sensitive values nested inside dict-valued keys (e.g., `{"headers": {"Authorization": "Bearer ..."}}`). Whether this matters depends on what gets logged at INFO level — if request headers aren't logged, the gap is theoretical (possible).

## Docker image runs as root

The final image has no `USER` directive. Adding a non-root user reduces blast radius if the app is compromised. The `COPY --from=ghcr.io/astral-sh/uv:latest` pulls the newest uv binary at build time without pinning, which could introduce breaking changes in CI.

## CI pipeline gaps

The security job uses `continue-on-error: true` on `pip-audit`, so vulnerable dependencies never block a merge. The test job runs without service containers (no Postgres, no Redis), relying on SQLite fallback — the Postgres/asyncpg code path that production uses is never validated in CI. The build job only runs on `main` pushes (not PRs), so a broken Dockerfile won't be caught until after merge.

## WebSocket idle timeout

The WebSocket location sets `proxy_read_timeout 86400` (24 hours). Stale connections from disconnected clients won't be cleaned up for a full day, accumulating file descriptors and upstream connection slots. A lower timeout (e.g., 3600s) with application-level ping/pong would bound resource consumption while still supporting long-lived sessions.
