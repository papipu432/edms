# Document Management System with LLM-powered wiki and RAG search

A greenfield FastAPI application that handles document upload (PDF, DOCX, images), encrypts PDFs at rest with pikepdf, runs a conversion/OCR pipeline to produce Markdown, indexes chunks in ChromaDB for vector search, and generates an auto-updating wiki of entities and topics via OpenAI. The architecture is straightforward: synchronous LLM calls inside an async background pipeline, module-level service singletons, and SQLite for both the relational store and ChromaDB persistence.

**Watch for:** hardcoded PDF encryption password shipped as default config (confirmed), unbounded prompt construction in both wiki query and chat that will hit token limits on any real corpus (confirmed), path traversal in the wiki page reader (confirmed), no authentication on any endpoint (confirmed).

## High-level view

The storage layer encrypts PDFs using a single password from `PDF_ENCRYPTION_PASSWORD`, which defaults to `"changeme"` in config and has no mechanism to rotate or derive per-document keys. Every user who downloads a PDF gets the same decryption password, so the encryption is theatrical unless the operator swaps it and controls who can call the download endpoint.

The document processing pipeline runs as a FastAPI `BackgroundTask` that creates its own DB session and engine. It chains conversion, summarization, keyword extraction, embedding, and wiki ingest synchronously. Because the LLM calls are blocking (synchronous OpenAI client), they block the thread inside an async background task, which will exhaust the default thread pool under concurrent uploads.

The wiki query endpoint reads the entire wiki into a single string and passes it as LLM context. The RAG chat endpoint concatenates the top-k chunks without truncation. Neither path accounts for token limits, meaning the system will start producing truncated or errored responses once the corpus grows past a few dozen documents.

The wiki page-read endpoint accepts arbitrary path segments (`/api/wiki/pages/{page_path:path}`) and resolves them relative to the wiki root without checking that the result stays inside that root. A request like `../../app/core/config.py` would expose source code and secrets.

The test suite (80 tests) thoroughly covers the happy paths and graceful degradation when no OpenAI key is present. It does not test concurrent pipeline execution, token overflow, or path traversal.

<summary>Issues (7)</summary>

1. **Hardcoded encryption password** — `PDF_ENCRYPTION_PASSWORD` defaults to `"changeme"` with no validation that it was overridden in production. Add a startup check or remove the default.
2. **Path traversal in wiki page reader** — `WikiService.get_page` resolves relative paths without constraining them inside `wiki_path`. Validate that the resolved path is a descendant of the wiki root.
3. **Unbounded wiki context in query** — `WikiService.query` concatenates all wiki pages into a single string passed as LLM context. Add truncation or retrieval filtering to stay within model token limits.
4. **Unbounded RAG context in chat** — The chat endpoint concatenates top-k chunks without checking total length against the model's context window. Truncate or dynamically reduce k.
5. **Blocking LLM calls in async pipeline** — Synchronous OpenAI calls inside `BackgroundTasks` will saturate the thread pool. Use the async OpenAI client or run the pipeline in a process pool.
6. **No authentication or authorization** — All endpoints (upload, download, delete, search, wiki) are open. Any client can read, modify, or delete any document.
7. **Module-level VectorDB singleton** — `search.py` creates a `VectorDBService()` at import time, making it impossible to override in tests without patching the class method, and locking in the production ChromaDB path regardless of environment.

## PDF encryption as access control

The system encrypts uploaded PDFs with pikepdf using AES-256 (R=6), which is a solid cipher. But the password is a single shared secret loaded from `settings.PDF_ENCRYPTION_PASSWORD` with a default of `"changeme"`. The download endpoint serves the encrypted file directly without ever prompting for or attaching the password, so the protection is only meaningful if the file is exfiltrated from disk and the attacker doesn't know the password.

```python
# config.py
PDF_ENCRYPTION_PASSWORD: str = "changeme"
```

There is no per-document or per-group key derivation. If the password leaks, every document in the system is compromised simultaneously. A production deployment should at minimum enforce that this value is set via environment and reject startup with the default.

## Path traversal in wiki page access

`WikiService.get_page` constructs a path by joining user input to the wiki root:

```python
def get_page(self, page_path: str) -> str | None:
    full_path = self.wiki_path / page_path
    if full_path.exists() and full_path.suffix == ".md":
        return full_path.read_text(encoding="utf-8")
    return None
```

The only guard is the `.md` suffix check, which means any `.md` file on the filesystem is readable — including files outside the wiki directory via `../../`. The API route uses `{page_path:path}` which permits slashes and dots. A request to `/api/wiki/pages/../../app/core/config.py` would fail the suffix check, but `/api/wiki/pages/../../some-secret.md` would succeed if such a file exists. The fix is to resolve the path and verify it starts with the wiki root.

## Prompt and context overflow

Two code paths construct unbounded LLM prompts:

1. **Wiki query** (`WikiService.query`): iterates every `.md` file in entities, topics, and summaries and concatenates them into a single context string. With 100 documents each producing entity and topic pages, this easily exceeds gpt-4o-mini's 128k context window and will produce API errors or truncated answers.

2. **RAG chat** (`app/api/search.py`): concatenates the top-k chunks (default 5, each up to 1000 chars) which is bounded today, but the system message preamble is already ~150 tokens. If `top_k` is raised via the request schema (no upper bound validation on `SearchRequest.top_k`), the same overflow applies.

`generate_summary` and `extract_keywords` both truncate input to 4000 characters, showing awareness of the issue — the same discipline should extend to the query paths.

## Blocking calls in the async pipeline

The pipeline orchestrator (`PipelineService.process_document`) is an async method that calls `generate_summary`, `generate_embeddings`, `extract_keywords`, and the wiki service synchronously. These use the synchronous `OpenAI` client, which blocks the calling thread. When invoked via `BackgroundTasks`, FastAPI runs the async coroutine on the event loop, but the synchronous HTTP calls inside it will block that loop iteration.

For a single upload this is fine. Under concurrent uploads, the event loop will stall on each blocking LLM call. The fix is either to use `AsyncOpenAI` with `await`, or to offload the entire pipeline to a thread or process pool (e.g., `asyncio.to_thread`).

## Module-level singletons and test isolation

Several modules instantiate services at import time:

```python
# app/api/search.py
vectordb_service = VectorDBService()

# app/api/wiki.py
wiki_service = WikiService(wiki_path=settings.WIKI_PATH)
```

This means the production ChromaDB path and wiki path are locked in the moment the module is imported. Tests work around this by monkey-patching (visible in `test_wiki.py` replacing `wiki_module.wiki_service`), but any test that forgets to patch will write into the production paths. The `search.py` tests patch `VectorDBService.search` at the class level rather than replacing the instance, which works but is fragile.

## CORS configuration

```python
app.add_middleware(
    CORSMiddleware,
    allow_origins=["*"],
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)
```

`allow_origins=["*"]` with `allow_credentials=True` is rejected by browsers (credentials require explicit origins), so this is effectively a no-credentials wildcard. It won't cause a browser exploit, but it signals the CORS configuration hasn't been thought through for a production deployment.

## Test coverage gaps

The test suite covers: CRUD operations on groups and documents, pipeline processing for PDF/DOCX/image conversion, LLM function graceful degradation, vector search indexing/querying/deletion, wiki ingest/query/lint/log, and all API endpoints with mocked LLM responses.

Not tested: concurrent pipeline execution (race conditions on the DB session), `top_k` validation or extreme values, path traversal on the wiki endpoint, the download endpoint returning an encrypted PDF that can actually be decrypted, token overflow behavior, or any authentication/authorization since none exists.
