# UX intelligence layer: tags, smart folders, templates, command palette, kanban, activity feed, and document intelligence pipeline

This change adds 12 features spanning two concerns: a UX productivity layer (command palette, kanban board, activity feed, breadcrumbs, onboarding tour, tags, smart folders, templates) and a document intelligence layer (LLM auto-tagging, form field extraction, citation detection integrated into the processing pipeline). Four new models (Tag, DocumentTag, SmartFolder, DocumentTemplate) and two new columns (Document.extracted_fields, User.onboarding_completed) support the new capabilities. Nine new API routers expose the features, and seven HTML templates provide the frontend.

The approach is breadth-first: each feature is a thin vertical slice from model through API to frontend, with the intelligence services connected to the existing pipeline via non-critical try/except blocks.

**Watch for:** Activity feed bypasses the existing audit permission check, exposing all audit logs to any authenticated user (confirmed). Smart folder ownership is not enforced on get/update/delete, allowing any user to read or modify another user's smart folders (confirmed). DocumentTag lacks a unique constraint on (document_id, tag_id), enabling duplicate associations on re-processing (confirmed). The `filename_contains` filter in smart folders interpolates user-controlled JSON values into a LIKE pattern without escaping wildcards (confirmed).

## High-level view

The activity feed is a second door into the same audit data that `/api/documents/{id}/history` gates behind `require_permission("audit", "read")`. The new `/api/activity/feed` endpoint only requires `get_current_user`, meaning any authenticated user can read the full audit trail including actions by other users on documents they may not have access to.

Smart folders introduce per-user saved queries, but the ownership model is incomplete. Listing filters by `owner_id == current_user.id`, yet get, update, and delete fetch by primary key without verifying the current user owns the folder. Any authenticated user can read, modify, or delete another user's smart folder by guessing or enumerating IDs.

The auto-tagging pipeline step blindly creates DocumentTag associations without checking for existing links, and since the table has no unique constraint on (document_id, tag_id), re-processing a document accumulates duplicate rows. The citation step is protected by DocumentRelationship's existing unique constraint, but the tag step has no such guard.

The smart folder query engine constructs LIKE patterns by directly interpolating `filename_contains` from the stored query JSON. While SQLAlchemy parameterizes the value (no SQL injection), LIKE wildcard characters (`%`, `_`) in the stored value are not escaped, enabling a user to craft a `filename_contains` of `%` to match all documents regardless of intent. The existing `search_enhanced.py` uses `_escape_like()` and `escape="\\"` for this purpose.

The `create-document-from-template` endpoint does not actually create a document — it returns the template's metadata as a JSON response. The frontend's `createFromTemplate` function expects a real document back (`doc.id`) and tries to redirect to `/documents/${doc.id}/view`, but the response contains `template_id` not `id`. This is a confirmed dead-end in the frontend flow.

The form extraction service accepts a custom `extraction_prompt` parameter (intended to be sourced from a template's `extraction_prompt` field), but the pipeline never passes it — it calls `extract_fields(sanitized_content)` without the second argument, so template-specific extraction prompts are never used.

5. **create-document-from-template is a stub** — The endpoint returns template metadata, not a created document. The frontend redirects to `/documents/${doc.id}/view` but the response has no `id` field. Either implement document creation or fix the frontend to handle the scaffolding response.

8. **Kanban loads all documents without pagination** — `/api/kanban` fetches every document-lifecycle pair in the system with no limit. At scale this becomes a performance problem and a large response payload.

## Activity feed as an authorization side-channel

The existing audit endpoint at `/api/documents/{id}/history` requires `require_permission("audit", "read")`:

```python
current_user: User = Depends(require_permission("audit", "read")),
```

The new activity endpoints at `/api/activity/feed` and `/api/documents/{id}/activity` only require `get_current_user`. Since the activity feed queries the same `DocumentAuditLog` table unfiltered, this effectively grants every authenticated user read access to the entire audit trail — including actions on documents they cannot otherwise access, actor usernames, and operational details stored in `details_json`.

## Smart folder ownership gap

Smart folder listing correctly filters by `SmartFolder.owner_id == current_user.id`, but the individual CRUD operations (get, update, delete, execute) look up by primary key without owner verification:

```python
folder = await db.get(SmartFolder, folder_id)
if not folder:
    raise HTTPException(status_code=404, detail="Smart folder not found")
# No check: folder.owner_id == current_user.id
```

This allows enumeration and manipulation of other users' saved queries.

## Duplicate tag associations in pipeline

The pipeline's auto-tagging block creates DocumentTag associations without existence checks:

```python
doc_tag = DocumentTag(document_id=doc_id, tag_id=tag.id)
db.add(doc_tag)
```

The API's `add_tag_to_document` correctly checks for existing links before creating them, but the pipeline code does not, and DocumentTag has no unique constraint on `(document_id, tag_id)`. Re-processing a document (e.g., on version upload) accumulates duplicate tag rows.

## LIKE wildcard injection in smart folder query engine

The smart folder document query constructs a LIKE pattern from user-controlled JSON:

```python
query = query.where(
    Document.original_filename.ilike(
        f"%{folder.query_json['filename_contains']}%"
    )
)
```

If `filename_contains` is set to `%` or `_`, the pattern becomes `%%%` or `%_%`, matching unintended rows. The existing `search_enhanced.py` solves this with `_escape_like()` and `escape="\\"`. The same applies to the command palette search endpoint which wraps `q` in `%{q}%`.

## create-document-from-template is incomplete

The endpoint returns template metadata without creating a document:

```python
return {
    "template_id": template.id,
    "template_name": template.name,
    "required_fields": template.required_fields,
    ...
}
```

The frontend JavaScript calls this endpoint and then tries:

```javascript
const doc = await resp.json();
window.location.href = '/documents/' + doc.id + '/view';
```

Since the response has `template_id` but no `id` field, this navigates to `/documents/undefined/view`.

## Template extraction_prompt disconnected from pipeline

The `DocumentTemplate.extraction_prompt` field exists in the model and is exposed via the API, but the pipeline calls `extract_fields(sanitized_content)` without the second argument. Since documents don't have a FK back to a template, the pipeline has no way to look up the relevant template and pass its prompt. The feature description (FEAT-004) states "if document has a template with extraction_prompt, or always try default extraction," but the wiring is absent.

## Kanban board unbounded query

The kanban endpoint fetches all document-lifecycle pairs with no limit or pagination:

```python
result = await db.execute(
    select(DocumentLifecycle, Document).join(...)
)
```

For a system managing thousands of documents, this returns an unbounded result set in a single response.

## Test coverage gaps

Not tested: the pipeline integration of auto-tagging/extraction/citation (no test verifies these steps execute during `process_document`). Not tested: the frontend JavaScript behavior (drag-and-drop, command palette, onboarding tour).
