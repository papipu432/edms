# EDMS enhancements: v1 fixes verified plus remaining template injection and scanner race (v2)

The five fixes from v1 review landed correctly: JWT secret startup warning, `escapeHtml()` across all templates, scanner temp directory cleanup, workflow role enforcement via `_ACTION_ALLOWED_ROLES`, and `chat_completion` migrated to direct `SystemMessage`/`HumanMessage` objects to avoid LangChain template interpolation. Three items were explicitly left unaddressed (document endpoint auth, JWT in localStorage, admin page server-side guard) and remain accepted trade-offs.

**Watch for:** the `chat_completion` template injection fix was not propagated to `extract_entities_topics`, `merge_content`, `generate_summary`, or `extract_keywords`, which still pass user-controlled text through `ChatPromptTemplate` (confirmed); the scanner endpoint deletes the temp file before the response is consumed, returning a dead path (confirmed).

## High-level view

The template injection fix in `chat_completion` uses direct Message objects (`SystemMessage`, `HumanMessage`) to bypass LangChain's brace-interpolation parser. But `extract_entities_topics`, `merge_content`, `generate_summary`, and `extract_keywords` were written using `ChatPromptTemplate.from_messages` with `{text}`, `{existing}`, and `{new_info}` placeholders. If any document content contains literal `{variable_name}` patterns — common in code, configuration files, and technical documentation — LangChain will either raise a `KeyError` for unrecognized variables or silently drop content between braces.

The scanner API endpoint calls `cleanup_scan()` immediately after building the `ScanResponse`. Since `ScanResponse.file_path` is just a string, the response body is valid JSON — but the path it advertises points to a deleted directory. Any caller that intends to read the scanned file at that path will get a `FileNotFoundError`.

## Template injection not propagated to remaining LLM functions

The `chat_completion` fix builds a `messages_list` of `SystemMessage` and `HumanMessage` objects and calls `model.invoke(messages_list)` directly, bypassing the template parser:

```python
# chat_completion — fixed
messages_list = [
    SystemMessage(content=system_content),
    HumanMessage(content=user_message),
]
result = model.invoke(messages_list)
```

The other four functions still use the vulnerable pattern:

```python
# extract_entities_topics — still vulnerable
prompt = ChatPromptTemplate.from_messages([
    ("system", "You extract structured information from text..."),
    ("human", "...Text:\n{text}"),
])
chain = prompt | model | StrOutputParser()
result_text = chain.invoke({"text": text[:4000]})
```

When `text` contains `{something}`, `ChatPromptTemplate` treats single braces as variable references. The `chain.invoke({"text": text[:4000]})` call supplies `text` but not `something`, so LangChain raises `KeyError("something")`. The except clause catches this and returns empty data, silently failing to extract entities from documents containing code or configuration samples.

The `merge_content` case is worse: if existing wiki content was merged from a document containing braces, subsequent merges will fail repeatedly because the brace-containing text persists in the wiki page. Each ingestion attempt for that page hits the same `KeyError`, and the fallback path does a naive string concatenation that duplicates content.

`generate_summary` and `extract_keywords` have lower probability of triggering because they process each document only once during pipeline ingestion, but any PDF containing source code, JSON samples, or template syntax will silently get empty keywords and a "generation failed" summary.

## Scanner file lifecycle race

The endpoint flow:

```python
file_path = scanner_service.scan(...)
response = ScanResponse(file_path=str(file_path), status="success", ...)
scanner_service.cleanup_scan(Path(file_path))  # deletes the directory
return response  # response.file_path → points to deleted file
```

The `file_path` field in the JSON response points to a removed directory. If the scanner API is meant to be consumed by another service that reads the scanned file from disk, this is a functional bug — the v1 fix for temp directory leaks overcorrected by cleaning up too eagerly.

The fix depends on intended usage: if callers need the file, remove the `cleanup_scan()` call from the endpoint and document that callers must clean up after consumption (or use a background task with a delay). If callers don't need the file on disk, serve the content inline and keep the cleanup.
