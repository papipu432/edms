# EDMS enhancements: Marker/Docling engines, LangChain migration, RBAC, and Jinja2 frontend

Four features land in a single change: pluggable PDF conversion engines (Marker/Docling) with OpenCV preprocessing, a LangChain migration replacing the raw OpenAI SDK, a JWT-based RBAC system with five roles, and a Jinja2 HTML frontend. The RBAC system handles user/role management and folder assignment, but does not enforce access control on the document CRUD endpoints themselves. The frontend stores JWT tokens in localStorage and renders server data via innerHTML without sanitization.

**Watch for:** document endpoints remain completely unauthenticated — any caller can upload, download, delete documents without a token (confirmed); JWT secret key defaults to a hardcoded value with no startup warning analogous to the existing PDF password check (confirmed); XSS in templates via innerHTML injection of user-controlled content like filenames and annotation text (confirmed); scanner service leaks temp directories on every scan (confirmed).

## High-level view

The conversion engine abstraction introduces a `ConversionEngine` enum and a try/preferred/fallback pattern in `convert_pdf()`. Marker and Docling each get a thin wrapper that delegates to the library's converter class. The fallback to PyMuPDF is well-structured, but the two new engines are import-gated and effectively dead code in environments where those heavy libraries aren't installed.

The LangChain migration replaces raw `openai.OpenAI()` calls with LCEL chains (`prompt | model | StrOutputParser`). The function signatures and return types are preserved so callers (pipeline, search, wiki) don't change. Two new functions (`extract_entities_topics`, `merge_content`) centralize logic that was previously inline in the wiki service.

The RBAC system provides JWT auth, password hashing, role assignment, and folder assignment models. However, the permission model is incomplete: folder assignments exist in the database but are never checked on document operations. The document, search, wiki, and scanner endpoints have no authentication dependency. Only the user management and annotation/workflow endpoints require a token.

The frontend is a set of Jinja2 templates using Tailwind and client-side JS that calls the API with `authFetch`. It stores the JWT in localStorage (accessible to any XSS payload) and renders API responses directly into the DOM via template literals and innerHTML. Several templates interpolate user-controlled strings (filenames, group names, annotation text, usernames) without escaping.

<summary>Issues (8)</summary>

1. **Document endpoints lack authentication** — `app/api/documents.py` has no `get_current_user` or `role_required` dependency. Any unauthenticated caller can upload, list, download, and delete documents. Add at minimum `get_current_user` as a dependency, and folder-level RBAC checks as described in FEAT-003's spec.
2. **Hardcoded JWT secret with no runtime warning** — `SECRET_KEY` defaults to `"changeme-secret-key-for-jwt"` in `config.py`. Unlike the PDF encryption password, there is no startup log warning when this value is in use. Add an equivalent `logger.warning()` in the lifespan function.
3. **XSS via innerHTML** — Templates render API-returned strings (filenames, group names, annotation text, usernames, wiki content) directly into innerHTML using JS template literals. A filename like `<img src=x onerror=alert(1)>` executes in the browser. Escape HTML before DOM insertion or use `textContent` for non-markup fields.
4. **JWT in localStorage** — Tokens stored in localStorage are accessible to any script on the page (including XSS payloads from issue 3). Consider httpOnly cookies, or at minimum fix the XSS vectors first.
5. **Scanner temp directory leak** — Both `TwainScanner.scan()` and `InsaneScanner.scan()` call `tempfile.mkdtemp()` but never clean up the directory. Over time this fills `/tmp`. Return a context manager or register cleanup in `ScannerService`.
6. **Workflow actions lack role enforcement** — Any authenticated user can approve, reject, or submit reviews on any document. The workflow endpoint only checks `get_current_user` without verifying the user holds the `approver` or `reviewer` role.
7. **Admin page accessible without server-side guard** — The `/admin/users` page route in `pages.py` has no authentication. The API call from the page will fail with 403, but the HTML is served to anyone. A server-side redirect or auth check prevents information leakage in the template markup itself.
8. **`chat_completion` prompt injection surface** — The RAG context is interpolated into the system prompt as a raw string, then the system prompt is passed through `ChatPromptTemplate` with a `{system_content}` variable. If context contains `{` or `}` characters, LangChain's template parser will raise or produce garbled output. Use a `MessagesPlaceholder` or escape the context.

## RBAC boundary gap

The FEAT-003 spec explicitly calls for "apply folder access checks to document endpoints in app/api/documents.py — upload requires editor/admin role for the group, download/view requires any assigned role." This was not implemented. The `documents.py` router has zero imports from `app.core.security`:

```python
# app/api/documents.py — no security imports
from app.core.config import settings
from app.core.database import get_db
from app.models.document import Document, DocumentStatus
...
```

Every document endpoint (`upload_document`, `list_documents`, `get_document`, `delete_document`, `download_document`, `get_document_markdown`) accepts any caller. The `FolderAssignment` model exists in the database but serves no enforcement purpose — it's write-only state that the admin UI manages but nothing reads for authorization decisions.

The annotation and workflow endpoints do require `get_current_user`, creating an inconsistency: you need a token to annotate a document but not to delete it.

## JWT secret and token management

`settings.SECRET_KEY` defaults to `"changeme-secret-key-for-jwt"`. The existing startup lifespan function already warns about the default PDF password:

```python
if settings.PDF_ENCRYPTION_PASSWORD == "changeme":
    logger.warning(...)
```

No equivalent check exists for `SECRET_KEY`. A deployer who sets the PDF password but forgets the JWT secret runs with a publicly-known signing key, allowing token forgery.

The token payload contains only `sub` (username) and `exp`. Roles are not embedded in the token — they're loaded from the database on every request via `get_current_user`. This is a reasonable choice for a system where roles change frequently, but it means every authenticated request issues a SELECT query against the users table with a `selectin` load of roles and folder assignments.

## XSS in frontend templates

Multiple templates use the pattern:

```javascript
list.innerHTML = groups.map(g => `
    <button ...>${g.name} ...</button>
`).join('');
```

The `g.name`, `d.original_filename`, `u.username`, `u.email`, `a.text` values all originate from user input stored in the database. If a user uploads a file with a malicious filename, every user who visits the dashboard will execute the injected script. The same applies to annotation text rendered in `document_viewer.html` and wiki entity names in `crossref.html`.

Combined with JWT-in-localStorage, a single stored XSS vector can exfiltrate every user's access token.

## Scanner resource lifecycle

Both scanner backends create a temp directory per scan:

```python
tmp_dir = Path(tempfile.mkdtemp())
output_path = tmp_dir / "scan.bmp"
```

The caller (`ScannerService.scan()`) returns the `Path` to the caller, which is the API endpoint `scan_document`. The endpoint converts this to a string response but never cleans up. There's no background task, no `finally` block, and no `tempfile.TemporaryDirectory` context manager. Each scan leaves an orphaned directory.

Additionally, `InsaneScanner` calls `pyinsane2.init()` and `pyinsane2.exit()` on every method call. If `scan()` raises between `init()` and `exit()`, the SANE backend is left in an initialized state which may block subsequent scans depending on the backend implementation.

## Prompt injection in `chat_completion`

The `chat_completion` function builds the system prompt by string-concatenating the RAG context, then passes it into a `ChatPromptTemplate`:

```python
system_content = (
    "You are a helpful assistant..." + context
)
prompt = ChatPromptTemplate.from_messages([
    ("system", "{system_content}"),
    ("human", "{user_message}"),
])
chain.invoke({"system_content": system_content, ...})
```

If `context` (which comes from user-uploaded document content) contains literal `{variable_name}` strings, LangChain will attempt to interpolate them as template variables. This will either raise a `KeyError` or silently drop content. The function should use `("system", system_content)` directly (a string message, not a template) or escape braces in the context.

## OpenCV pipeline color loss

The `opencv_pipeline` method chains `opencv_adaptive_threshold` → `opencv_morphological_denoise` → `opencv_deskew`. Both threshold and denoise convert the image to grayscale internally. When `opencv_deskew` then runs on the resulting single-channel array, it works fine. But the pipeline always returns a grayscale image regardless of input. For OCR this is acceptable, but the docstring doesn't mention this behavior, and the method is exposed publicly — a caller using it for non-OCR preprocessing (e.g., image display) would lose color data unexpectedly.

## Annotations list endpoint is unauthenticated

`GET /api/documents/{document_id}/annotations` has no `get_current_user` dependency:

```python
@router.get("/api/documents/{document_id}/annotations", ...)
async def list_annotations(document_id: int, db: AsyncSession = Depends(get_db)):
```

Creating an annotation requires authentication, but reading annotations does not. If annotations contain sensitive review comments, this is an information leak.
