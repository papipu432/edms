# Batch 4: Obsidian integration, multi-tenancy, and platform services

This batch adds eleven features: bi-directional Obsidian vault sync, a wiki graph visualizer, daily note generation, canvas/whiteboard with Obsidian .canvas export, a system health score dashboard, scheduled report CRUD with manual trigger, multi-tenant model and middleware, offline package generation, bulk import/export, webhook integrations with HMAC signing, and an Obsidian plugin specification. The approach is additive across the board -- new models, services, API routers, and HTML templates, with no modifications to existing production code paths beyond adding a `tenant_id` column to the `Document` model.

Watch for: **`hmac.new` does not exist** in Python's `hmac` module -- the webhook signing service and its test will crash at runtime (confirmed). Zip-based import paths (Obsidian sync and import/export) perform **no path traversal validation**, allowing a crafted zip to write files outside the intended directory (confirmed). The **multi-tenant middleware is never registered** and no queries filter by `tenant_id`, so the feature is structurally inert (confirmed). The **webhook secret is returned in API responses** via `WebhookResponse` (confirmed).

## High-level view

The Obsidian sync service implements a file-hash-based conflict resolution strategy (Obsidian wins for user pages, EDMS wins for summaries) driven by a manifest persisted on disk. The design is sound, but the zip extraction path trusts filenames without sanitization, creating a zip-slip vector.

The canvas subsystem is a straightforward three-table CRUD (Canvas, CanvasItem, CanvasConnection) with an Obsidian .canvas export endpoint. It lacks owner-based authorization on get/update/delete -- any authenticated user can access any canvas by ID.

Multi-tenancy is introduced as a Tenant model and middleware, but the middleware is not mounted and no service or query filters data by `tenant_id`. It's a schema-only placeholder that currently provides no isolation.

The webhook service signs payloads with `hmac.new(...)`, which will raise `AttributeError` because Python's `hmac` module exposes `hmac.HMAC` (class constructor) or the deprecated `hmac.new` only in very old versions -- the correct call is `hmac.new` on Python 2 but `hmac.HMAC` or the shorthand in Python 3. The test duplicates the same broken call, so it won't catch the failure.

Offline package generation and import/export share a zip-building pattern that conditionally includes files from `doc.storage_path`. The export path imports `pathlib.Path` inside a loop body (minor), and the import path creates `Document` records pointing to `/imported/...` paths that don't actually exist on disk, so re-export after import would produce empty placeholders.

## Zip-slip in Obsidian sync and import/export

In `ObsidianSyncService.import_zip`, zip entry names are used directly:

```python
for name in zf.namelist():
    if name.endswith(".md") and not name.startswith("__"):
        content = zf.read(name)
        zip_files[name] = content
```

Later:

```python
full_path = self.wiki_path / path
full_path.parent.mkdir(parents=True, exist_ok=True)
full_path.write_bytes(content)
```

A zip entry with path `../../etc/cron.d/backdoor.md` passes both guards (ends with `.md`, doesn't start with `__`) and results in a write to an arbitrary location relative to `wiki_path`. The fix is to resolve the destination and confirm it stays within `wiki_path`:

```python
resolved = (self.wiki_path / path).resolve()
if not resolved.is_relative_to(self.wiki_path.resolve()):
    continue  # or raise
```

The same pattern exists in `ImportExportService.import_zip` where `name.split("/")` builds paths without containment checks.

## `hmac.new` does not exist in Python 3

`app/services/webhooks.py` line 30:

```python
return hmac.new(
    secret.encode("utf-8"),
    payload.encode("utf-8"),
    hashlib.sha256,
).hexdigest()
```

Python 3's `hmac` module does not expose a function called `new`. The correct invocation is:

```python
return hmac.HMAC(
    secret.encode("utf-8"),
    payload.encode("utf-8"),
    hashlib.sha256,
).hexdigest()
```

The test (`tests/test_webhooks.py` line 191) duplicates the same broken call, so it validates the bug rather than catching it.

## Webhook secret in API responses

`WebhookResponse` schema:

```python
class WebhookResponse(BaseModel):
    id: int
    url: str
    secret: str  # <-- plaintext secret returned to client
    ...
```

Webhook secrets are HMAC signing keys. Returning them in list/get responses means any admin who can call the API (or any log that captures response bodies) leaks the signing material. Standard practice is to either omit the field in responses or return a masked version (e.g., `"****...last4"`).

## Canvas authorization gap

The list endpoint correctly scopes to `Canvas.owner_id == current_user.id`, but get/update/delete/items/connections endpoints use only `Canvas.id == canvas_id` with no owner check:

```python
result = await db.execute(select(Canvas).where(Canvas.id == canvas_id))
```

Any authenticated user who guesses or enumerates canvas IDs can read, modify, or delete another user's canvas. Add `.where(Canvas.owner_id == current_user.id)` to all single-canvas queries, or implement a shared-canvas permission model.

## Multi-tenant isolation is structural placeholder only

The `Tenant` model exists, `Document.tenant_id` is a nullable FK, and the middleware sets `request.state.tenant_id` from the `X-Tenant-ID` header. But:

- The middleware is never registered in `app/main.py`.
- No endpoint or service reads `request.state.tenant_id`.
- No query adds `.where(Document.tenant_id == ...)`.

The CRUD for `/api/tenants` works (create, list, update, delete tenants), but creating a tenant has no effect on data isolation. This is fine as a first step if documented as incomplete, but would be dangerous if shipped under the assumption that tenants are isolated.

## Obsidian sync memory pressure and no file-size guard

The sync import endpoint reads the entire uploaded zip into memory:

```python
zip_data = await file.read()
```

There's no `Content-Length` check or streaming extraction. A 2GB zip upload would allocate 2GB of RAM before any processing begins. For a service handling document management, this is a practical denial-of-service vector. Consider adding a `max_size` parameter or streaming the zip from a `SpooledTemporaryFile`.

## Wiki graph synchronous file I/O on async endpoint

`app/api/wiki_graph.py` iterates all wiki pages and calls `full_path.read_text(encoding="utf-8")` synchronously inside an `async def` endpoint. For a wiki with hundreds of pages, this blocks the event loop for the duration of all those file reads. Wrapping the heavy I/O in `asyncio.to_thread` or pre-building the graph data would prevent latency spikes.

## Scheduled reports: generation produces static HTML, no actual data

`ScheduledReportService.generate_report` accepts a `db` session but never queries it -- every report type returns a hard-coded HTML string with a timestamp:

```python
def _generate_weekly_summary(self, timestamp: str) -> str:
    return (
        "<h2>Weekly Summary Report</h2>"
        f"<p>Generated: {timestamp}</p>"
        "<p>Summary of document activity for the past week.</p>"
    )
```

The `trigger_report` endpoint logs "sending" but doesn't actually send email (it instantiates `EmailNotificationService` but never calls it). This is presumably intentional scaffolding, but worth noting that the test asserts `status in ["delivered", "failed"]` without verifying any content was actually generated from real data.
