# Collaboration and workflow batch 2: approvals, comments, locks, signatures, delegations, SLA

Six collaboration features added to the EDMS: multi-stage approval chains with folder/template matching, threaded comments with @mention notifications, document checkout locks with expiry, SHA-256 e-signatures with QR verification, delegation of approval authority, and SLA tracking with breach detection. Each feature is self-contained with its own model, schema, API router, and test file. The workflow builder HTML page provides a UI for approval chain management.

**Watch for:** Approval decisions have no authorization check on who can decide a step (confirmed). The signature service accepts raw PEM private keys over the network (confirmed). Delegations exist as a standalone feature but are never consulted by the approval flow (confirmed). The SLA breach check endpoint has no concurrency protection (confirmed).

## High-level view

The approval chain system models multi-step sequential/parallel workflows but the `decide_approval` endpoint permits any authenticated user to approve or reject any step, regardless of whether they hold the required role or are assigned to that step. This is the most significant authorization gap in the batch.

The signature service generates SHA-256 hashes of document content concatenated with user ID and timestamp, then offers public verification. The signing endpoint optionally accepts a PEM-encoded private key in the request body, which means private key material transits the network and passes through application memory.

Delegations are structurally complete (create, list, revoke, lookup by user) but serve no functional purpose yet: the approval decision flow never checks whether the deciding user holds a delegation from an assigned approver. The API exists, the data model exists, the integration does not.

The document lock system uses a unique constraint to prevent double-locks, cleans up expired locks on read, and gates admin force-unlock properly. However, locks are advisory-only: no document mutation endpoint checks lock status before allowing edits.

The `list_comments` endpoint requires no authentication, which exposes comment content on access-controlled documents to any caller who knows the document ID.

SLA tracking provides policy management, deadline computation, breach detection, and a dashboard. The `check-breaches` endpoint loads all active SLAs into memory and has no protection against concurrent execution causing duplicate breach notifications.

<details>
<summary>Issues (8)</summary>

1. **Approval decision has no step authorization** — Any authenticated user can approve/reject any step. The endpoint should verify the user matches the step's `role_code`, `user_id`, or holds an active delegation. (`app/api/approval_chains.py`, `decide_approval`)
2. **Private key accepted over HTTP** — The `sign_with_certificate` path accepts PEM private key material in the request body. Private keys should never leave the client; consider accepting only a certificate/public key for verification, or use a server-side signing ceremony. (`app/api/signatures.py`, `sign_document`)
3. **Delegations not integrated with approvals** — The delegation model and API exist but are never checked during `decide_approval`. A delegate cannot currently act on behalf of a delegator. Wire the delegation lookup into the approval authorization check.
4. **SLA breach check is not idempotent under concurrency** — Two concurrent calls to `check-breaches` can both read the same SLA as non-escalated and both create breach notifications. Add a database-level guard (e.g., `SELECT ... FOR UPDATE`) or make the notification creation conditional on a CAS-style status update.
5. **Locks are advisory-only** — No document update/upload endpoint checks whether the document is locked by another user. Locks prevent nothing without enforcement at the mutation layer.
6. **Comments list endpoint is unauthenticated** — `GET /api/documents/{document_id}/comments` requires no authentication token. If documents are access-controlled, comments should respect the same boundary.
7. **SLA dashboard loads all SLA records into memory** — `sla_dashboard` does `select(DocumentSLA)` with no filter, then counts in Python. Use SQL aggregation (`COUNT ... GROUP BY status`) instead.
8. **Parallel approval type has no behavioral difference** — Steps can be declared `parallel` but the approval flow always advances to the next `step_order` on a single approval. Parallel semantics (requiring N approvals at the same step order) are not implemented.

## Approval decision authorization gap

The `decide_approval` endpoint in `app/api/approval_chains.py` retrieves the current step (which has `role_code` and optionally `user_id` fields) but never checks whether `current_user` matches either:

```python
# This is all the "authorization" that happens:
current_step = result.scalar_one_or_none()
if not current_step:
    raise HTTPException(status_code=404, detail="Current approval step not found")

# Immediately records the decision from whoever called
decision = ApprovalDecision(
    request_id=request_id,
    step_id=current_step.id,
    user_id=current_user.id,
    ...
)
```

The step stores `role_code` (e.g., "reviewer") and `user_id` but neither is compared against the acting user. Any authenticated user can approve or reject any pending request. The tests confirm this pattern: a single admin user creates and decides all steps, so the gap is never exercised.

This is also the natural integration point for delegations: if the step is assigned to user A but user B holds an active delegation from A, B should be permitted to decide.

## Private key in flight via signature service

`sign_with_certificate` in `app/services/signature_service.py` deserializes a PEM private key received from the client:

```python
def sign_with_certificate(content_bytes: bytes, cert_pem: str) -> str | None:
    private_key = serialization.load_pem_private_key(
        cert_pem.encode("utf-8"), password=None
    )
```

The field is named `certificate_pem` in the schema but expects a private key (it calls `private_key.sign()`). This conflates certificate and private key semantics. Sending a private key to a server defeats the purpose of asymmetric cryptography. If server-side signing is intended, the key should be stored server-side in a key store, not transmitted per-request. If client-side signing is intended, the client should sign locally and send only the signature bytes for storage.

The bare `except Exception: return None` silently swallows malformed key errors, making signing failures impossible to diagnose from the caller's perspective.

## SLA breach detection at scale

The `check-breaches` endpoint loads every active SLA into a Python list and iterates:

```python
result = await db.execute(
    select(DocumentSLA).where(
        DocumentSLA.status.in_([SLAStatus.on_time, SLAStatus.at_risk])
    )
)
active_slas = list(result.scalars().all())
```

The computation (`_compute_percent_elapsed`) is simple arithmetic that could be expressed as a SQL CASE expression in an UPDATE statement, avoiding the full-table load into application memory.

The concurrency concern is more immediate: two simultaneous calls will both see `sla.escalated = False`, both set it to `True`, and both create a breach notification. Without row-level locking or an atomic conditional update, duplicate notifications are expected under concurrent invocation.

## Document lock enforcement gap

`app/api/documents.py` never consults lock status. A user can upload a new version of a locked document because nothing blocks them. The lock is purely informational until document mutation endpoints (upload, update metadata, delete) check it and reject writes from non-lock-holders.

## Parallel approval semantics

The `ApprovalType` enum includes `parallel` alongside `sequential`, and steps can be created with either type. However, the decision flow treats them identically: one approval on the current step advances to the next `step_order`. True parallel semantics would require multiple approvals at the same step order (e.g., 3 out of 5 reviewers must approve). The step model doesn't include a quorum field, and the decision logic doesn't count existing decisions for the same step.
