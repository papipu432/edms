# Collaboration workflow batch 2: v2 fixes verified (v3)

All three issues from the v2 review have been addressed. The approval authorization path now has test coverage for the 403 denial and delegation-based access. The signature endpoint returns 422 when `private_key_pem` is provided but invalid. The delegation scope check now filters on `scope_type` and `scope_folder_id`, preventing folder-scoped delegations from authorizing decisions on unrelated chains.

**Watch for:** No blocking concerns remain.

**Verdict**: APPROVED

## High-level view

The `_check_active_delegation` function now accepts a `folder_id` parameter and constructs an `or_` filter requiring either `scope_type == 'all'` or a matching `scope_folder_id`. The caller (`decide_approval`) fetches the chain's `folder_id` and passes it through. This closes the scope-bypass gap.

The signature endpoint's certificate-signing block now checks the return value of `sign_with_certificate` and raises `HTTPException(status_code=422)` when the result is `None`, making invalid-key failures distinguishable from no-key-provided.

Three new tests exercise the non-admin authorization paths: a 403 when a user lacks the required `role_code`, a 201 when a user has the correct role, and a 201 via delegation with assertion that the response comment mentions the delegation. These cover the previously-dead `if not is_admin` branch.

## Delegation scope filter

The v2 review flagged that `_check_active_delegation` ignored `scope_type` and `scope_folder_id`. The fix introduces:

```python
scope_filter = or_(
    Delegation.scope_type == DelegationScopeType.all,
    (Delegation.scope_type == DelegationScopeType.folder)
    & (Delegation.scope_folder_id == folder_id),
)
```

The `decide_approval` endpoint fetches `chain.folder_id` and passes it as the third argument. When `folder_id` is `None` (chain has no folder), the folder-scoped branch of the `or_` won't match any delegation row with a non-null `scope_folder_id`, so only `scope_type == 'all'` delegations will authorize — which is the correct behavior.

## Signature 422 on invalid key

The fix is minimal and correct:

```python
if data and data.private_key_pem:
    certificate_data = sign_with_certificate(content_bytes, data.private_key_pem)
    if certificate_data is None:
        raise HTTPException(
            status_code=422, detail="Invalid private key or signing failed"
        )
```

Callers providing a key now get explicit failure feedback instead of a silent 201 with `certificate_data: null`.

## Authorization test coverage

`test_decide_approval_denied_without_required_role` creates a user with `["editor"]` role and attempts to decide a step requiring `"reviewer"` — asserts 403. `test_decide_approval_with_correct_role` creates a user with `["reviewer"]` and asserts 201. `test_decide_approval_via_delegation` creates a delegation with `scope_type="all"` from the assigned user to a delegate, asserts 201 and checks the delegation annotation in the comment. Together these exercise all three non-admin authorization paths (user_id match is implicitly covered by the delegation test setup where the assigned user exists but the delegate acts instead).
